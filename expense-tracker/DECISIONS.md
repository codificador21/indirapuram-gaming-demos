# DECISIONS

Every judgement call made while building this unattended, with the reason and how to change it.
Newest entries are appended at the bottom of each section.

## Project layout & tooling

### D1. The app lives in `expense-tracker/`, not the repo root
- **Chose:** a self-contained folder inside `indirapuram-gaming-demos`.
- **Why:** the repo root is an existing static site (landing page + demos, likely served by GitHub
  Pages). Putting a Next.js app at the root would break or clutter it.
- **Change it:** `git mv expense-tracker/* .` into a new repo (it has no dependency on the rest of
  this repo), or set the host's "root directory" to `expense-tracker` (DEPLOY.md does this).

### D2. Drizzle ORM instead of Prisma
- **Chose:** Drizzle + `pg` (node-postgres), SQL migrations generated by `drizzle-kit` and committed
  in `drizzle/`.
- **Why:** no query-engine binary to download at install/build time (a common failure point in
  sandboxes, Docker builds and on PaaS), plain SQL migrations you can read, and types inferred from
  the schema file. As a Postgres person you can read every query.
- **Change it:** the schema is one file (`src/db/schema.ts`); `prisma db pull` against the migrated
  database generates an equivalent Prisma schema.

### D3. Versions pinned exactly
- Next.js 16.4 (App Router, Turbopack), React 19.3, Tailwind 4.3, Drizzle 0.45, Recharts 3,
  Vitest 5, TypeScript **5.9** (not 7.x — TS 7 is the new Go-based compiler and the Next/ESLint
  ecosystem plugins are not guaranteed to support it yet), ESLint **9** (eslint-config-next is
  validated against 9).
- vitest 4.1 triggered an npm resolver crash (`Cannot read properties of null (reading
  'edgesOut')`) via its optional browser peer deps; vitest 5.0.5 installs cleanly, so I used it.
- **Change it:** bump in `package.json`, run `npm run check`.

### D4. `npm audit` findings are dev-only
- `npm audit` reports advisories in `braces`/`micromatch` (via `eslint-config-next`) and an old
  `esbuild` (via `drizzle-kit`). Both are development tools that never run in production or touch
  user input, and the suggested "fixes" downgrade to ancient majors. Left as is.

### D5. Money in integer paise, enums as text
- Amounts are `bigint` paise everywhere (DB and code) — no floating point rounding.
- Status/direction/channel columns are `text` typed via TypeScript unions (`src/lib/domain.ts`)
  rather than Postgres enums, so adding a value never needs an `ALTER TYPE` migration.

### D6. Timezone is explicit
- "Today", day grouping and budget periods use `APP_TIMEZONE` (default `Asia/Kolkata`) via `Intl`,
  never the server's local time (Railway/Render servers run in UTC — 00:00–05:30 IST would otherwise
  land on the wrong day).

### D7. Default categories are created by `db:migrate`, not by a SQL migration
- `scripts/migrate.ts` runs the SQL migrations and then upserts the built-in categories from
  `src/lib/categories.ts` and the singleton settings row. One source of truth, safe to re-run on
  every deploy. Renamed categories / custom colours are preserved.

## Parsing & ingestion

### D8. Parser = per-format templates + generic fallback
- **Chose:** `src/lib/parser/formats.ts` holds one named-group regex per known alert layout (HDFC,
  ICICI, SBI, Axis, Kotak, Paytm, PhonePe, GPay — SMS and email). When no template matches,
  bank-agnostic extractors in `generic.ts` try each field on their own. Fixtures in `fixtures.ts`
  (49 samples) each have a test.
- **Why:** templates give exact, predictable results for the formats I actually receive; the generic
  layer means a slightly changed bank format still usually parses instead of falling to review.
- **Change it:** to support a new format, paste the alert into `fixtures.ts` with the expected
  result, add a template, `npm test`.

### D9. What counts as noise (ignored, but still stored)
- OTPs, promos, payment-due / statement / "will be debited" reminders, declined/failed
  transactions, UPI collect requests, balance-only messages, and messages with no amount and no
  money verb. They are saved with `status = ignored` and visible under Review → Ignored, so a
  misclassified message can still be turned into a transaction.
- A message must have a past-tense money verb *and* account/card/UPI evidence to escape the promo
  filter, which keeps "get ₹500 cashback credited" offers out.

### D10. Everything that is not clearly parsed goes to the Review inbox
- Missing amount or direction → `needs_review`. Nothing posted to the webhook or matched by the
  email filter is ever dropped.

### D11. Dedupe rules
1. Same normalised reference (UPI RRN/UTR/txn id) + same amount + direction → duplicate (any time
   apart).
2. If *both* sides have a 12-digit UPI RRN and they differ → **not** a duplicate, even within the
   time window (two ₹20 chais 3 minutes apart are two payments).
3. Otherwise same amount + direction + compatible account (last digits match or one unknown) +
   occurred within **±10 minutes** → duplicate.
- References in other formats (PhonePe `T26…` ids, SBI ATM 4-digit numbers) don't block rule 3,
  because SMS and app receipts often carry different id types for the same payment.
- Also: the *same message text* within ±1 hour (Shortcut retry, or an SMS also forwarded by email)
  is recorded as `duplicate/same_message`, and an email Message-ID is processed only once.
- Duplicates enrich the existing transaction (fill missing ref, balance, account, payee).
- Concurrency: ingestion takes a Postgres advisory lock, so an SMS and its email arriving in the
  same second can't both create a transaction.
- **Known gap:** a bank email that arrives >10 minutes after a card SMS *without* any reference
  will create a second transaction. Widen `DEDUPE_WINDOW_MS` in `src/lib/dedupe.ts` if this happens.

### D12. Non-salary credits ("credit kind")
Every credit gets a `creditKind` that decides how it affects the budget:

| Kind | Detected when | Budget effect |
| --- | --- | --- |
| `salary` | text says salary/SAL/payroll, **or** amount within 2% of my configured salary, **or** 60–160% of salary via NEFT/IMPS/RTGS within ±4 days of the salary day | none (the budget already comes from the salary setting) |
| `refund` | refund / reversal / cashback / chargeback, or a credit from a known merchant (e.g. `swiggy.refunds@…`) | **offsets spending** (reduces net spend, filed under the merchant's category) |
| `reimbursement` | person-to-person UPI credits (VPA that looks like a name, Axis `P2A`, …) | **offsets spending** — friends paying back their share of a bill |
| `income` | interest, dividends, unknown NEFT/IMPS credits, anything else | ignored by the daily budget |

- **Why:** refunds and split-bill paybacks undo money that was already counted as spent, so
  counting them makes "safe to spend" honest. Unknown big credits (a freelance payment, a gift)
  should *not* silently inflate daily spending money — that's a decision for me to make.
- **Change it:** tap a credit → "How should this credit count?" in the UI, or change the rules in
  `classifyCredit()` (`src/lib/classify.ts`).

### D13. Exclusions from the budget (auto-detected)
- **Credit-card bill payments** (bank debit "towards … credit card", CRED, BillDesk card payments,
  and the card's "payment received" credit) are excluded — card spends were already counted when
  swiped; counting the bill again would double-count.
- **Self-transfers**: payee matches one of my names/VPAs (Settings → "That's me"), a beneficiary
  "A/c XX1234" that is one of my accounts, the word "self", or an automatic **pair**: a debit on
  one account and a credit of the same amount on another account within 30 minutes (IMPS/NEFT/UPI,
  not card spends or merchant refunds). Both halves are excluded and linked.
- **Fixed commitments**: a debit within ±10% of a commitment's amount whose text contains one of its
  keywords (e.g. SIP ₹5,000 with keyword `zerodha`) is excluded — it was already subtracted from the
  monthly budget.
- I can always toggle "Exclude from budget" on any transaction; un-excluding one half of a detected
  pair releases both.

### D14. Categorisation
- Precedence: card-bill/self-transfer → my learned rules → ATM = Cash / salary / income → keyword map
  (longest keyword wins, so "Swiggy Instamart" is Groceries but "Swiggy" is Food) → person-to-person
  = "People" → Other.
- Re-categorising in the UI with "Remember for <merchant>" (on by default) saves a rule keyed on the
  normalised merchant name and re-files past auto-categorised transactions from that merchant (not
  ones I set by hand). A rule key also matches a longer name when only a generic suffix is added
  (`amazonpay` → `amazonpayindia`), but not a different merchant that happens to share a prefix
  (`swiggy` ≠ `swiggyinstamart`). Suffix list: `GENERIC_SUFFIXES` in `src/lib/categorise.ts`.

### D15. Webhook auth and payload
- `POST /api/ingest/sms` requires `Authorization: Bearer $INGEST_TOKEN` (constant-time compare).
  The token is never accepted in the query string (it would end up in logs).
- Payload `{ text, sender?, receivedAt? }`; aliases (`message`, `body`, `from`, `date`) and a
  plain-text body are accepted because Shortcuts are hand-built. `receivedAt` can be omitted — the
  automation runs the instant the SMS arrives, so server time is accurate; ISO, epoch and the
  default Shortcuts date formats are understood.

## Budget

### D16. "Safe to spend today" is fixed at the start of the day
- **Chose:** today's allowance = (monthly budget − net spend *before today*) ÷ days left *including
  today*. The big number on Home is what's left of it: allowance − net spend today (can go
  negative). The naive fixed figure (budget ÷ days in month) is shown next to it, plus "tomorrow"
  (what tomorrow's allowance becomes if I stop spending now).
- **Why:** the spec's formula re-evaluated after every purchase barely moves when I spend (₹500
  spent today only lowers it by ₹500/11), so the number would keep saying I can spend more. Fixing
  it at the start of the day makes it a real daily allowance; rollover still works exactly as
  specified across days (under-spend carries forward, over-spend shrinks future days).
- **Change it:** `computeBudget()` in `src/lib/budget.ts`.

### D17. Budget month = calendar month (salary cycle optional)
- The spec says "days in the current month", so the default period is the calendar month.
  Settings → "Budget cycle" can switch to salary-day → day-before-next-salary-day (handy if salary
  lands on the 25th–31st). Salary day 31 clamps to the month's last day.
- Monthly budget = configured net salary − active fixed commitments (never below zero). Actual
  salary credits don't change it; they are tagged `salary` for the record.

### D18. Net spend
- Debits count; refunds and reimbursements subtract; salary/other income and excluded rows
  (self-transfers, card bill payments, fixed commitments, manual exclusions) are ignored.
- Category charts show gross spend per category, with refunds/paybacks shown as a separate line,
  so no category ever shows a negative bar.

## UI

### D19. App name "Kharcha"
- Short enough for the iPhone home-screen label, and means "expense" in Hindi.
- **Change it:** `APP_NAME` in `src/lib/theme.ts` (+ the icon in `public/icons/`).

### D20. Dark by default, theme in a cookie
- The theme is stored in an `et_theme` cookie and rendered on the server (`<html data-theme>`), so
  there is no light→dark flash on load. Toggle on Home (sun/moon) or Settings → Appearance.
- Colours are CSS variables in `src/app/globals.css`; light and dark values are chosen separately
  (not an automatic inversion).

### D21. Charts
- **Category spend:** horizontal bars in a single hue, sorted, with the amount at the bar tip, top 8
  + "N more categories". The list *is* the data table. (A donut with ~18 categories would need more
  distinguishable colours than exist.)
- **Daily spend vs budget:** columns = spend per day, line = that day's rollover budget, one rupee
  axis, legend + tooltip + "Table" toggle. Days where refunds exceeded spending draw as ₹0 bars
  (tooltip/table show the real negative net).
- **Month so far vs even pace:** cumulative spend vs a straight budget line.
- Series colours (blue spend, orange budget) were run through a colour-vision-deficiency validator
  for both themes. Status colours (amber/red) only appear with an icon and a text label.

### D22. Mobile interactions
- Tap a transaction → bottom sheet: one tap on a category saves it (and, by default, remembers it
  for that merchant) and closes the sheet. Exclude-from-budget and credit kind toggle instantly
  (optimistic), notes/merchant/amount/date have a Save button.
- Swipe a row left → quick "Category" and "Exclude/Include" buttons.
- Quick add: amount field is focused with the numeric keypad, Cash is pre-selected, typing a
  merchant I've used before pre-selects its category, and the form resets after Save for
  back-to-back entries.

### D23. PWA
- `app/manifest.ts` + icons (PNG rendered from `public/icons/icon.svg`; regenerate with any
  SVG→PNG tool at 180/192/512 px) + `apple-mobile-web-app-*` meta → "Add to Home Screen" opens
  full-screen with its own icon.
- `public/sw.js` (registered in production only): cache-first for hashed static assets, network-first
  for pages with an offline fallback page. API calls and server actions are never cached.

### D24. Auth
- One password (`APP_PASSWORD`) → 30-day HS256 JWT in an httpOnly, SameSite=Lax cookie (Secure in
  production). `src/proxy.ts` gates every page; every server action re-checks the session.
- 8 wrong passwords within 15 minutes locks login for the rest of that window (in-memory, per
  instance — fine for one user on one instance).

## Email

### D25. IMAP poller as a separate process (+ cron endpoint)
- `npm run worker` polls every `IMAP_POLL_INTERVAL_SECONDS` (default 120 s) and backs off up to
  15 minutes on repeated failures. Without IMAP env vars it logs "disabled" and exits 0, so the web
  app never depends on it.
- Alternatives for hosts without a worker: `npm run poll:once` (cron job) or
  `POST /api/cron/poll-email` with the ingest token (any external cron), or Settings → "Check email
  now".
- Only **unseen** mail from the last `IMAP_LOOKBACK_DAYS` is considered. For each message only the
  envelope is read first; mail that isn't from a known bank/UPI sender (or tagged
  `IMAP_SUBJECT_TAG`) is never downloaded or flagged. Processed mail is marked `\Seen`
  (`IMAP_MARK_SEEN=false` to leave it unread); the Message-ID is stored so it is never ingested
  twice either way.
- Tested end-to-end against an in-memory IMAP server (`hoodiecrow-imap`) in
  `tests/email-poller.integration.test.ts`.

## Later additions

### D26. "Re-check with latest parser"
- Review → *Re-check with latest parser* re-runs the current parser over everything in Needs review
  and Ignored. Anything that now parses goes through the same dedupe/classification as new
  messages (so it links to an existing transaction instead of double counting).
- Workflow when a bank changes its SMS format: add a fixture + template, deploy, tap Re-check.

### D27. Category "People"
- Person-to-person payments (both directions) live in one category called **People** (id
  `transfers`). Paybacks from friends land there too and offset spending (see D12).

### D28. Seed and fixture data are fictional
- Names (Aarav Mehta, Rahul Sharma…), account numbers, VPAs and UPI references in fixtures and the
  seed are made up. The seed refuses to run on a database that already has transactions unless you
  use `npm run db:reset`, which wipes transactions, messages, rules, commitments and accounts.

### D29. No `output: 'standalone'`
- Railway runs `npm start` (`next start`), which doesn't work with standalone output. If you move to
  a Docker image later, add `output: 'standalone'` back in `next.config.ts` and run
  `node .next/standalone/server.js`.
